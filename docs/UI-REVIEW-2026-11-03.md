審查基準:`feat/cost-basis` @ `f4b7ba5` · 196 項離線測試全綠 · 四道 CI 關卡本機全過

這一輪只看呈現層:版面、可用性、以及呈現層自己做的決策。引擎的正確性由
`test/golden`、`test/invariant`、`test/parity` 負責,不在這裡重複。

## 方法

不靠肉眼。在真瀏覽器(Chromium)載入本機靜態伺服器,以
**1440 / 1240 / 1100 / 1024 / 768 / 390 / 360** 七個寬度逐一量測,
每個寬度把五個 view 都切過一遍,對每個葉節點元素收集三件事:

| 量測 | 判準 |
|---|---|
| `scrollWidth − clientWidth` | > 1px 即為文字被切掉 |
| 元素矩形 vs 最近的 `.card` 矩形 | `right` 超出即為跑出卡片 |
| `button / input / select / a` 的高度 | < 40px 在手機上即為觸控目標過小 |

量測用的資料是合成持倉(七位數總值、六檔標的、一檔 0 股、一檔成本未知),
不是實際持倉。**這個 repo 是公開的,實際數字一個都不進版控。**

## 第一部分 · 已修正

### 1. 加碼試算完全沒有閘門 —— 唯一一個會影響決策的

**重現**:全新裝置(或清掉 localStorage)→ 持倉頁 → 填金額 → 按「算這筆錢該怎麼分」。

**行為**:回報「每一檔都已達到或超過加碼後的目標權重——這筆先留在現金」。

**為什麼錯**:那句話是假的。真正發生的是 `Q.px` 是空的,`allocateCash` 裡
每一檔的 `priceTWD` 都回 `null`,`gaps` 是空陣列,`total` 為 0,於是落進
「都已達標」那個分支。**它把「抓不到價」講成「不用買」**,而新裝置正是
最常遇到這個的時候。

**更嚴重的第二層**:`computeState` 的 `risk` 來自
`prior.signal ? prior.signal.risk_flag : undefined`。沒有訊號時是 `undefined`,
`allocateCash` 的 `if (st.risk)` 閘門等於不存在 —— **崩盤裡照樣產生買單**。
`btnAuto` 一直都有 `sigBad(Q.sig)` 的檢查,`btnAdd` 是唯一的例外。

這與上一輪「貼上解析在新裝置 `sure` 全是 false」是同一類:
功能在沒有報價時會**無聲降級**,而且降級後的輸出看起來像正常輸出。

**修正**:填了金額就先補抓報價,再過 `EG.gateReasons` 的五道閘門才分配,
與 `btnAuto` 一致。新增四項測試,其中三項以突變測試驗證(拆掉就紅)。

### 2. 標的配置的名稱欄被壓成碎片

**重現**:設定頁 → 標的配置,視窗寬 1024px 或任何手機寬度。

**量測**:390px 時名稱 `<input>` 的 `scrollWidth − clientWidth = 211px`;
1024px 時 186px。實際可見寬度只有 **2px**(390px)與 **36px**(1024px)。

**成因**:那一列是
`grid-template-columns:92px 1fr 62px 76px 56px`,五個控制項裡只有名稱欄是
`1fr`。固定欄加間距共 340px,卡片內寬不足 460px 時 `1fr` 就被擠成碎片。
卡片內寬的計算:

```
手機:  W − 32(main padding) − 40(card padding)      → 390px 時 318px → 名稱 −22px
1024:  1024 − 200(側欄) − 64 − 24 − 320(.sec-row 標籤欄) − 40 → 376px → 名稱 36px
1440:  1176 − 320 − 24 − 40 = 792 → 名稱 452px ✓
```

**後果**:手機上**看不到也改不了任何標的的名稱**。這不是美觀問題。

**修正**:行內樣式收進 `.instrow`,1240px 以下改成兩行
(代碼+% / 名稱+類別+刪除)。修正後 360px 的名稱欄可見寬度 124px。

### 3. 首列五格在 1240px 以下互撞

**量測**:1024px 時「組合總值 1,311,745」溢出自己那一格 **32px**,
直接疊在「現金水位」上面。

**成因**:`.strip.lead` 是 `repeat(5,1fr)`,格寬
`(1024 − 264) / 5 = 152px`,扣掉 18px 內縮剩 116px;
26px 的 IBM Plex Mono 每字元約 15.6px,`1,311,745` 共 9 字元 = 140px。

**修正**:`901–1240px` 改成 3+2 兩列。
`≤389px` 兩欄時每格只剩 126px,字級降到 22px —— 八位數的總值可容納,
**九位數仍會溢出**,這是已知上限。

同一個寬度帶裡,壓測頁 `.cols` 的 1.4fr 欄只剩 430px,
三欄表格每一格都在折行(「本機驗證」折成「本機驗」/「證」),一併改單欄。

### 4. 其餘

| 問題 | 證據 | 修正 |

## 第二部分 · 看過但刻意不改

**`.strip.lead b{font-size:26px}` 看起來多餘,其實不是。**
`.strip b` 的優先序是 (0,1,1),`.big` 只有 (0,1,0) —— **`.strip b` 贏**。
首列的數字是 26px 全靠檔尾那條 `.strip.lead b`。刪掉會讓它縮成 20px。
這條規則脆弱但正確,留著。

**`makePlan` 裡的 `cf > tc * 1.05` 是裸數字。**
不是 `REARM`(那是分層遲滯的 5%),是另一個 5%。黃金案例與平價測試都釘著
這個行為,改成具名常數是純重新命名,會動到 `engine.json` 與 CI 第 2 關,
換不到正確性。留著。

**壓測頁 1241px 以上仍有約 95px 的參差空白。**
左卡(表格+註)比右卡(按鈕+註)高。這是外觀不是破損,且兩張卡的高度
本來就不可能齊平。今日頁當初是 160px 且永遠無法齊平才重構成三條整寬帶;
這裡的代價不值得。

**年度再平衡、板塊乖離篩選器**:見上一輪的結論,不做。

**壓測頁的「水下時間」與「今天在歷史分布的位置」**:提案過,你還沒說做,
沒動手。

## 第五部分 · 券商庫存貼截圖(2026-11-03,PR #8)

**問題**:貼圖片進 `<textarea>` 不會留下任何文字,所以按「解析」得到的是
「這段文字裡找不到任何已設定的標的代碼」—— 那句話在回答一段空字串,
沒說錯但完全沒幫到人。

**方案**:Tesseract.js 7.0.0 按需載入,只載 eng。代碼、股數、市值、損益率
全是 ASCII,中文名稱根本不需要讀。辨識在裝置上跑,圖片不送伺服器。
沒貼圖的人一個位元都不會下載。

**架構**:OCR 只是「把圖變成文字」的輸入管道。辨識完的文字放進同一個框,
解析與核對完全走 `parseBrokerPaste`。那套「股數 × 現價 ≈ 市值」正好是
OCR 最需要的保險 —— 認錯一個數字,兩邊就對不上,那一列變成「需確認」。

### 實測抓到的真問題:代碼結尾的 L 被認成 1

合成截圖四列,**一列中招**:`00647L` → `006471`。那一檔**整列無聲消失** ——
代碼對不上就不進解析表,也不會被列進「設定頁沒有的代碼」,畫面上沒有
任何線索。而台股槓桿 ETF 每一檔都以 `L` 結尾,這不是邊角,是系統性的。

`fixOcrCodes` 的規則刻意很窄,因為它在決定「這一列的錢屬於哪一檔」:

1. 只比對設定頁裡實際存在的代碼(封閉集合,不是開放式猜測)
2. 長度必須相同,且只准差一個字元
3. 那個字元必須與目標同屬一個已知互混群組 —— **雙向**:OCR 可能把 `1`
   看成 `l`,也可能把 `L` 看成 `1`。第一版用單向對照表,`0063lL` 修不到
4. 符合條件的目標必須唯一;兩個都像就不改

修完的文字放回輸入框讓人看見。它住在引擎(碰錢的判斷要有真測試),
但 `parseBrokerPaste` **刻意不呼叫它** —— 打字打錯的 `006471` 不該被悄悄
改成 `00647L`,那是 OCR 專屬的修補,不是解析規則。

### 端對端實測

深色底白字的合成券商截圖(760×420,四列)→ 辨識 **3.9 秒** →

| | 股數 | 市值 | 回推成本 |
|---|---|---|---|
| 00631L | 2,000 | 67,500 | 68,134 |
| 00670L | 500 | 92,200 | 99,214 |
| 00647L | 300 | 41,280 | 40,078 |

數字逐字正確,成本由損益率回推(41,280 / 1.03 = 40,078 ✓),
`00897` 正確回報為設定頁沒有的代碼。中文名稱全是亂碼 —— 不影響,
解析只看代碼與數字。

### 又踩到同一個坑:兩道假綠

- 共用的 `INST` 代碼是單字母 `A` / `B`,而 `fixOcrCodes` 不處理三字元以下
  的代碼 —— 突變等於沒套用上,測試當然綠
- 「兩個都像時不改」那題,我給的兩個代碼其實一個都沒命中

兩題都改成真的會碰到那道防線的情境,並加上**反向斷言**(先證明單獨一個
的時候確實會修),免得空結果是別的原因造成的。

**結論三度確認**:突變測試的價值全在「突變真的改到了檔案、而且那段程式
真的被測試情境執行到」。只看紅綠不看情境,等於什麼都沒驗。

## 第六部分 · 大改:結論先講、五頁併三頁(PR #10)

### 問題

這個 App 每個月只回答一個問題:「要不要動、動什麼」。
而那個答案**從來沒有被講出來** —— 使用者得自己讀完整張訂單清單,
才推得出「這個月要下六筆單」。第一次打開更慘:一排 0 加一段列舉五道
閘門的長文,沒有任何一句話告訴人下一步做什麼。

### 結論先講

今日頁最上面是一句話,40px(手機 30px):

| 狀況 | 結論 | 副標 |

| 再平衡 | 本月要下 6 筆單 | 把每一檔拉回目標比例,現金留 20%。 |
| 無動作 | 本月無動作 | (引擎的 hold 訊息) |
| 風險期 | 風險期:減碼 3 筆 | 把現金拉回 50%,這次最多賣掉手上持股的 50%。 |
| 閘門擋下 | 本月不下單 | 下面這幾道沒過⋯⋯ |
| 第一次打開 | 還沒有持股 | 到「設定」把券商庫存貼上來⋯⋯ |

### 修法:不靠負號,用三個數字互推

市值、損益金額、損益率本來就互相閉合:

```
虧損 → 成本 = 市值 + |損益| = 市值 ÷ (1 − |損益率|)
獲利 → 成本 = 市值 − |損益| = 市值 ÷ (1 + |損益率|)
```

兩個解各自推回損益率,誰接近畫面上印的那個誰就是答案。**比損益率而不是
比損益金額**:畫面印的就是損益率,拿同一個量來比才不會被四捨五入放大。
決定之後用「市值 ± 損益金額」當成本——兩個整數,比四捨五入到兩位小數的
損益率精確。

原本的實作只用了市值與損益率,**損益金額那一欄整個丟掉**,而它正是裁決
符號的關鍵。

### 判不出來的時候說判不出來

|損益率| 很小時兩解幾乎重疊,符號從數字上就是判不出來。此時
`costSure:false`,預覽表把那一格標成「需確認」並說明原因。
猜一個然後裝作確定是最糟的選項。
