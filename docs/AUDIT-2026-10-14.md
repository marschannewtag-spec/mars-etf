# 第一部分 · 架構全貌

## 1.1 一句話

這是一個**決策輔助台**,不是交易系統。它讀市場資料、算出「這個月該買賣什麼」、
把清單給人看。**人去券商下單。任何自動化都不碰券商帳戶。**

```

  ├─ fetchAll()          8 個請求並行(實測序列 825ms → 並行 110ms)
  │    ├─ /signal        ★ 唯一允許 reject 的;失敗 = 整個中止

  ├─ 閘門(blockers)     任一成立即中止,且不推進峰值與分層

  │
  ├─ EG.computeState()   → {V, cash, cf, tc, dd, risk, miss}
  │
  ├─ EG.makePlan()       三條路徑(見 1.5)
```

## 1.5 決策三路徑

```
makePlan(ctx, st)
│
├─ st.risk === true ─────────────── 風險期
│   ├─ cf < DEF - CASH_EPS
│   │   ├─ hold <= 0 → hold:「無持股可減」      ← 防 NaN,曾是 bug
│   │   └─ sell = min(DEF*V - cash, CAP*hold)
│   │       每檔 nu = floor(cur * (1 - sell/hold))
│   │       → kind:"trim", targetCash: DEF
│   └─ cf 已達 → hold:「空手等待旗標熄滅」
│   ★ 絕不投入、絕不再平衡
│
└─ st.risk === false ───────────── 正常期
    act = (dd <= T30 && cf > tc*1.05)          分層抄底可投入
        | |cf - tc| > DRIFT * tc               現金偏離超帶
        | 任一標的 |w - tg| > DRIFT * tg       權重偏離超帶
    │
    ├─ !act → hold:「全部在容忍帶內」
    └─ act  → 每檔 nu = floor(targetWeight(i,tc,inst) * V / pt)
              若 |nu-cur|*pt < V * MIN_TRADE_FRACTION 則 nu = cur(避免碎單)
              → 無訂單則 hold:「整數化後無需交易」
              → 否則 kind:"rebalance", targetCash: tc
```

## 1.6 分層階梯與遲滯

```
LADDER = [[-0.50, 0.05], [-0.40, 0.10]]   必須由深到淺排列
BASE   = 0.20     REARM = 0.05

dd <= -50% → 目標現金 5%    (最積極抄底)
dd <= -40% → 目標現金 10%
否則       → 目標現金 20%   (BASE)

遲滯:want > prev(要鬆綁回較高現金)時,
      回撤必須改善超過「原門檻 + REARM」才放行,
      否則維持 prev。防止在門檻上下反覆進出。
```

## 1.7 狀態模型

**持久化狀態**只有兩個,存在 `localStorage.etf2x`:

| 欄位 | 意義 | 推進時機 | 污染後果 |
|---|---|---|---|
| `S.peak` | 組合歷史峰值 | 僅 `render(true)` 且閘門全過 | 回撤計算全錯,分層階梯誤判 |
| `S.tierTc` | 目前分層目標現金 | 同上 | 配置目標錯誤 |

其餘(`units`/`cashTWD`/`cashUSD`/`inst`/`prem`/`log`/`worker`/`cap`/`ccy`)是使用者輸入。

**設計核心:閘門不推進狀態。** 資料不完整時若推進峰值,會把錯誤的低估值
記成新峰值,之後所有回撤計算永久污染,而且沒有任何跡象。

# 第二部分 · 已確認的缺陷

每一條都標示**驗證方式**。所有「已驗證」的項目都實際執行過程式碼。

## 【P1】2.1 不變量層只檢查數字,不檢查訂單 —— 人執行的正是訂單

`checkInvariants` 驗證 `plan.units`(非負整數)、`plan.cash`(有限非負)、
現金守恆、`targetCash` 範圍、風險期無買單、減碼不超 CAP。

**它完全沒有驗證 `plan.orders` 與 `plan.units` 是否自洽。**

使用者拿去券商執行的是 `orders`;App 事後記錄的是 `units`。
兩者若分歧,券商部位與 App 紀錄會無聲走偏,而下一次月檢會以錯誤的
`units` 為基礎繼續計算。

**驗證方式**:取一個正常計畫 `{orders:[{X, buy, 380}], units:{X:480}}`,
把訂單方向反轉成 `sell`、股數改成 `99999`、`units` 完全不動,
送進 `checkInvariants` →

```
>>> 不變量攔下嗎: []
```

**完全放行。**

**應有的不變量**:對每筆訂單,`units[id] - units0[id]` 必須等於
`±shares`,且 `side` 必須與差額同號;未出現在訂單中的標的,
`units[id]` 必須等於 `units0[id]`。

> 註:這需要 `checkInvariants` 能取得 `units0`,目前 `ctx.units` 就是,
> 所以簽章不必改。

## 【P1】2.2 輸入側零驗證 —— 不變量只守出口,不守入口

`checkInvariants` 守的是引擎**產出**。引擎**輸入**(`S.units` 等)
沒有任何驗證。開機時只做 `S.units = S.units || {}`,逐鍵不檢查。

**驗證方式**:`units = {X: -500, Y: 100}`、價格皆 100、現金 100,000 →

```
totals:         {"inv":-40000,"cash":100000,"V":60000,"miss":false}
computeState:   {"V":60000,"cf":1.6666666666666667,"dd":-0.7,...}
計畫:            rebalance ["X buy 800","Y buy 80"]
>>> 不變量:      []
```

後果鏈:

- `inv` 為負 → `V` 被低估
- `cf` = 166.7%(現金佔比超過 100%,物理上不可能)
- **`dd` = -70%** —— 憑空捏造的回撤。這會直接觸發分層階梯最深一格
- `miss` = false → **閘門不會擋**
- `render(true)` 會把這個錯誤的 V 寫進 `S.peak`,**永久污染**
- 不變量全數放行

**入口**:匯入 JSON(`impFile.onchange` 只檢查「是非陣列物件」,
其餘照單全收後寫入 localStorage 並 reload),或手動編輯 localStorage。

**對照:同類攻擊在另一條路徑上是被擋住的。** 匯入把 `tierTc` 設成 0.99 →

```
tc=0.99 → rebalance X sell 990
>>> 不變量: ["目標現金 0.99 超出 [0.05, 0.5]"]
```

**攔下了。** 原因是 `tc` 會流進 `plan.targetCash`,而 `targetCash` 有範圍檢查。
`units` 不流進任何被檢查的欄位,所以無人看守。

這就是防護的不對稱:**純量有人守,向量沒人守。**

---

## 【P1】2.3 目標權重全為 0 → 建議清倉 100%,不變量放行

**驗證方式**:兩檔標的 `tgt` 皆為 0,各持 100 股 @ 500 →

```
weightSum fallback = 0.8
總值 100000 → rebalance A sell 100, B sell 100
計畫後現金 100000 = 100.0% 總值
不變量: []
>>> weightsSumToOne: false
```

**建議全部賣光、現金 100%,且不變量一句話都沒說。**

兩個獨立問題:

1. `weightSum()` 在總和為 0 時回傳魔術數 `0.8`。這個 fallback
   **掩蓋了錯誤**而非處理它——回傳 0.8 之後 `targetWeight` 仍然是
   `(1-tc)*0/0.8 = 0`,所以 fallback 根本沒救到任何東西,只是讓
   除法不爆炸,然後靜靜產生清倉建議。

2. `weightsSumToOne()` 這個函式**存在、被匯出、在 `invariant.test.js:111`
   被測試**,但**沒有接進 `checkInvariants`**。能抓到這個情況的工具已經寫好了,
   只是沒插上電。

## 【P2】2.4 扳機沒有遲滯 —— 而且已經在實際抖動

00653L(富邦印度正2)的扳機條件是 `Brent > 90 AND USD/INR > 96`。
監控只在 `armed` 翻轉時通知。

**從心跳提交還原的真實軌跡**:

```
2026-09-08  brent  100.69  inr 95.11  armed off
2026-09-14  brent  101.23  inr 95.94  armed off   ← 距觸發 0.06
2026-09-15  brent  107.43  inr 95.94  armed off   ← 距觸發 0.06
2026-09-16  brent  102.05  inr 95.93  armed off   ← 距觸發 0.07
2026-09-28  brent   99.86  inr 95.97  armed off   ← 距觸發 0.03
2026-09-29  brent   96.80  inr 95.97  armed off   ← 距觸發 0.03
2026-10-01  brent  100.96  inr 96.31  armed ON    → Issue #1
2026-10-07  brent  101.48  inr 96.77  armed ON
2026-10-09  brent  104.25  inr 96.72  armed ON
2026-10-12  brent  106.69  inr 95.76  armed off   → Issue #2
2026-10-13  brent  105.77  inr 95.27  armed off   ← 目前
```

三件事同時成立:

1. **Brent 自 09-08 起就一直在 90 以上**(現為 105.77)。
   第一條腿已經連續鎖定兩個月,整個扳機完全掛在 INR 的雜訊上。
2. **INR 在整個九月反覆貼著 96 的門檻**(95.93 / 95.94 / 95.97),
   最近只差 0.03。這是教科書等級的門檻抖動。
3. **12 天內已經產生 2 個 Issue**,而且一次完整的「觸發→解除」循環
   只維持了 9 個交易日。

分層階梯有 `REARM = 5%` 的遲滯來防止這件事;**扳機一點遲滯都沒有**。
同一個問題在一個地方解決了,在另一個地方沒有。

**後果**:若 INR 繼續在 96 附近震盪,使用者會固定收到成對 Issue,
然後學會忽略它們。那時真正的風險旗標翻轉也會一起被忽略。

**缺少的功能**:「單腿武裝 / 接近觸發」的預警。
目前使用者對「Brent 已經破 90 兩個月、INR 只差 0.8%」完全沒有能見度——
只有在兩條腿同時成立的那一瞬間才會被告知。

## 【P2】2.5 扳機門檻不在 PARAMS —— 唯一正在發作的參數,卻沒有單一真相

`90` 與 `96` 這兩個數字出現在:

| 位置 | 形式 |
|---|---|
| Cloudflare Worker | **權威值**(原始碼不在本 repo) |
| `test/contract.test.js:87` | 硬編碼,用來反向驗證 Worker |
| `monitor/check.js:159` | 硬編碼在**通知訊息字串**裡 |
| `index.html` | 硬編碼在**畫面文字**裡 |

## 【P3】2.12 「整數化後無需交易」訊息不準確

這則訊息有兩個不同的成因,但措辭只描述了其中一個:

1. 真的是整數化造成的(目標股數與現有股數相同)
2. **`MIN_TRADE_FRACTION` 抑制**(`|nu-cur|*pt < V*0.005` → 強制 `nu=cur`)

第 2 種情況下,使用者看到「整數化」會以為部位已經對齊,
實際上是「差距存在但小於最小交易門檻,刻意不動」。這兩件事的意義不同。

**關於小權重標的的死區**(我原本的假設,已驗證為**基本不成立**):

條件是 `act=true`(偏離 > `DRIFT*tg`)但無交易(差距 < `MIN_TRADE_FRACTION`),
即偏離落在 `(0.25·tg, 0.005)` 這個區間。要讓這個區間非空需 `tg < 2%`。

實測 `tg = 1.951%` 的標的,偏離 4 倍容忍帶 → **仍然正常產生訂單 194 股**。
因為該區間寬度僅 `0.005 - 0.25×0.01951 = 0.00012` = 總資產的 0.012%,
實務上碰不到。預設組合最小權重 5%,更不可能。

**結論:死區在數學上存在,實務影響可忽略。真正要修的是訊息措辭。**

## 【P3】2.13 匯入是信任邊界,但 `worker` 位址未經確認

```js
r.onload=function(){
  const o=JSON.parse(r.result);
  if(!o||typeof o!=="object"||Array.isArray(o))throw "格式錯誤";
```

唯一的驗證是「是非陣列物件」。`S.worker` 會被直接覆寫。

## 【P3】2.14 離線即停機 —— 重構引入的回歸

沒有 service worker。manifest 是 data: URI,只讓它可安裝,不提供離線快取。

單一檔案版本不可能有這個失敗模式。多檔案重構之後,
離線開啟 PWA 會顯示:

```
⛔ 引擎載入失敗
找不到 engine/engine.js。本頁不再是單一檔案...
```

**使用者無法分辨「我離線」與「部署壞了」。** 對一個每月開一次、
可能在行動網路下開啟的工具,這是實質的使用性回歸。

**建議**:加一個最小 service worker,快取 `index.html` + `engine/engine.js`,
並在引擎載入失敗時先檢查 `navigator.onLine` 以給出正確訊息。
